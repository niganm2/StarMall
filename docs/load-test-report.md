# 星购商城 压测报告

- 测试日期：2026-11-01
- 压测脚本：[scripts/loadtest](../scripts/loadtest/README.md)
- 测试目的：验证两级缓存、Sentinel 限流、用户维度频控的实际效果，以及延迟关单链路的闭环正确性

## 1. 测试环境

| 项目 | 说明 |
|---|---|
| 压测端 | Windows 宿主机，Python 3 + aiohttp，异步并发发压 |
| 被测端 | 同机部署的网关（8080）与 7 个微服务（JDK 11） |
| 中间件 | VMware 虚拟机 192.168.100.128：MySQL、Redis、Nacos、Seata 1.5.2、RabbitMQ 3.8（含 delayed-message 插件）、Milvus |
| 数据量 | 在售商品 ID 池 88476 条 |
| 压测方式 | 固定并发数 + 固定时长，统计 TPS、平均响应、P50/P95/P99 |

> 重要前提：压测端与被测服务在同一台物理机上，客户端会与被测服务争抢 CPU 和端口资源，因此数据只适合同场景纵向对比，不代表系统极限。

## 2. 场景一：商品查询 500 并发

| 组别 | 并发 | 时长 | 总请求 | TPS | 平均响应 | P99 | 说明 |
|---|---|---|---|---|---|---|---|
| A 热点 ID（缓存命中） | 500 | 30s | 未记录 | **2547** | **195.9ms** | 288.8ms | 预热 3s 后两级缓存命中 |
| B 随机 ID（回源 MySQL） | 500 | 30s | 未记录 | **1223** | **408.0ms** | 564.2ms | 压测前 `FLUSHDB` 清空 Redis |
| C 限流接口（`/items?ids=`） | 500 | 15s | 9016 | 601 | — | — | Sentinel QPS 限流生效 |

C 组明细：15 秒总请求 9016，成功 754，其余 8262 被限流；通过速率约 **50 次/秒**，与配置的 `QPS=50` 一致。

**结论**

1. 缓存命中组吞吐为回源组的 **2.08 倍**（2547 vs 1223 TPS）。
2. 500 并发下平均响应从 408ms 降到 195.9ms，降幅约 **52%**。
3. 缓存组几乎不产生数据库读请求，真正价值是把读流量挡在 MySQL 之外。

## 3. 场景二：10 并发（纯净单请求耗时）

| 组别 | 并发 | 时长 | 平均 | P50 | P99 |
|---|---|---|---|---|---|
| A 缓存命中 | 10 | 15s | **5.5ms** | 5.4ms | 9.5ms |
| B 回源 MySQL | 10 | 15s | **7.4ms** | 7.4ms | 13.4ms |

**结论**：低并发下两者只差 1.9ms。原因是 Redis 与 MySQL 都在同一台虚拟机上，都是一次内网往返，而主键单查本来就快。**缓存的收益体现在高并发吞吐，而不是单次延迟**——这一点在面试中被追问时应当主动说明。

## 4. 场景三：下单接口 500 并发

冒烟（单笔）：HTTP 200，耗时 **97.6ms**，库存 10000 → 9999，确认扣减真实生效。

| 指标 | 数值 |
|---|---|
| 总请求（15s） | 7117 |
| 成功 200 | 9 |
| 限流拒绝 400 | 7108 |
| 其他异常 | 0 |
| 总 TPS | 454 |
| 成功请求平均响应 | 3794ms（P50 3835ms，P95 5982ms） |

拒绝响应样例：`{"code":400,"msg":"下单过于频繁，每 60 秒最多 10 次，请稍后再试"}`

**结论**

1. 99.87% 的请求在进入业务逻辑前被用户维度频控拒绝，MySQL、Seata、MQ 均未被压到。
2. 成功订单响应慢是**排队效应**：7108 个被拒请求与 9 个下单请求共享 Tomcat 线程池；串行下单热态仅 124ms。
3. 15 秒后库存由 9999 回到 10000，未支付订单被延迟消息关闭并回补，账实一致。

## 5. 场景四：下单接口 1000 并发

| 指标 | 数值 |
|---|---|
| 总请求（15s） | 8404 |
| 成功 200 | 9 |
| 限流拒绝 400 | 8394 |
| 其他异常 | 1（HTTP 500） |
| 总 TPS | **265**（低于 500 并发时的 454） |
| 拒绝请求平均响应 | 1849ms（P95 2348ms） |

**结论**：并发翻倍后 TPS 反而下降。瓶颈在压测端与服务同机、Tomcat 默认 200 线程排队，以及同一 SKU 下单时的 Seata 全局锁竞争，不是服务端容量上限。这组数据用于说明单机压测的局限，不作为性能指标。

## 6. 场景五：延迟关单闭环验证

| 检查项 | 结果 |
|---|---|
| `trade.delay.direct` 类型 | `x-delayed-message`（插件已生效） |
| `pay.direct` 交换机 | 已创建并绑定 `trade.pay.success.queue` |
| 下单后 1.5 秒库存 | 10000 → 9999（扣减生效） |
| 12 秒后订单状态 | `status=5`（已关闭），`close_time` 比 `create_time` 晚 12 秒 |
| 关单后库存 | 9999 → 10000（回补正确） |
| 串行 5 笔热态耗时 | 124 / 114 / 119 / 123 / 140 ms，平均 **124ms** |

> 12 秒 = 10 秒延迟 + 消费处理耗时，符合设计预期。

## 7. 总体结论

1. **读链路**：两级缓存把 500 并发的读吞吐提升一倍，平均响应降低约一半；单请求延迟几乎不变，收益在并发场景。
2. **写链路**：条件更新 + 行数校验保证不超卖；500 并发下库存扣减与回补完整闭环。
3. **入口防护**：Sentinel 精确按 50 QPS 放行；用户滑窗把 99.87% 的下单请求挡在业务层之前，两层防护互补。
4. **异步关单**：延迟消息插件生效，10 秒关单 + 库存回补已实测通过，与支付成功实时通知形成双链路。

## 8. 局限性（面试时应主动承认）

1. 压测端与被测服务同机，1000 并发数据受客户端和线程池瓶颈影响，不能作为系统上限。
2. 未采集 MySQL QPS、连接池使用率、JVM GC 等资源指标，只有接口层数据。
3. 部分组别的 P50/P95 未记录（A/B 组仅记录平均与 P99）。
4. 下单压测全部命中同一 SKU（317578），存在全局锁竞争，不代表多商品场景。
5. 单机单实例，未覆盖集群、网关多副本、Nacos 多节点等高可用场景。
